## 二、测试构成

### 2.1 业务内核单测（120 条，tests/test_unit_core.py）
纯函数层验证，不依赖数据库：

- 工具函数：四舍五入（q0/q2/q4/q6）、安全数值、除零保护、期间推算（跨年 / 闰月天数）
- 折标煤：电 0.0001229 tce/kWh、天然气 1.33 tce/千m³ 等系数换算与聚合
- 碳排：范围一/二拆分（柴油/天然气 vs 电力/蒸汽/水/压缩空气）、energy 编码回退、碳强度
- 能耗强度：6 位精度单耗（防小量级失真）、单位产值能耗、同比环比
- 分时电费：四时段（尖峰 1.28 / 峰 1.02 / 平 0.68 / 谷 0.34）逐时段电费、校验差恒 0
- 容量电费：按需量 / 按容量双模式；力调电费 ±15% 封顶、加收与减免方向
- 需量：15 分钟电量 → kW 换算、四级状态（正常 / 预警 85% / 紧急 95% / 超容 100%）、最大需量
- 设备能效：空压机比功率（≤6.3 优 / ≤7.2 良）、水泵效率、锅炉热效率、制冷机 COP、劣化 5% 判定
- 节能量：(基线单耗 − 报告期单耗) × 产量、年节费（标煤 620 元/tce）、回收期、月度年化
- 告警：需量分级、单耗偏离基线三级（8% / 15% / 30%）、汇总统计
- 抄表质量：表底差 × 倍率、倒走判定、量级跳变（3 倍且 >100）、换表用量、覆盖率、缺口补值
- 能源平衡 / 预算闸口（90% 预警 / 100% 超支 / 110% 阻断）
- 权限：7 角色 × 27 权限矩阵完整性、边界角色断言

### 2.2 接口测试（147 条，tests/test_api.py）
真实 HTTP 服务 + 临时 SQLite，覆盖 69 路由中的 45+ 端点：

- 健康检查、静态资源、OpenAPI、/apidoc、404 兜底
- 鉴权：登录 / 登出 / 我的信息 / 改密（含旧口令校验）、五通道令牌（Bearer / X-Fp-Token / Cookie / ?token= / X-Fp-Key）
- 权限：7 角色逐一边界（reader 只读、finance 只读预算、engineer 不可验证项目等）
- 主数据：介质 / 中心 / 产线 / 计量点 / 设备 CRUD 与筛选
- 抄表三闸口：**倒走 409 / 区间重叠 409 / 跳变入库+自动告警**，批量部分成功语义
- 分时/需量：四时段汇总、需量上报分级、连续超容无编号冲突、同刻 upsert
- 分析报表 11 个：看板（含范围一/二守恒断言、电力为第一大介质）、能耗分析排序、单耗基线、同比、排名、平衡、日报、碳排、CSV 导出（UTF-8 BOM）
- 基线：创建 / 重复 409 / 无产量 409
- 能效：四类设备计算器、测试录入、劣化告警
- 项目：创建（无基线 409）、验证（无基线 / 无计量 / 产量 0 三闸口）、结果落库
- 告警：筛选、排序（紧急优先）、处置（二次处置 409）、权限
- 预算：预警 / 超支 / 阻断状态、upsert
- 系统：用户（停用即拒登）、规则动态生效（改 demand_warn_ratio=0.5 后需量 54% 即预警）、API Key 生命周期（明文仅一次、越权 403、删除即失效）、Webhook、审计日志
- 集成：增量同步 6 实体、Idempotency-Key 幂等回放、CORS、OPTIONS 预检、限流放行

### 2.3 冒烟脚本（31 项，tools/smoke_api.py）
对**运行中的实例**做端到端验收（不建库），含数据断言：

- 健康检查（路由 ≥69、计量 ≥30、抄表 ≥300）
- 看板守恒（scope1 + scope2 = total、介质拆分非空、电力居首）
- 能源平衡闭合、分时四时段守恒、抄表覆盖率区间
- 能效计算器精确值（比功率 5.76 → 优）
- OpenAPI / 增量同步 / 13 种事件
- 未授权 401 / 越权 403 / CSV BOM

### 2.4 UI 巡检（17 项，tools/ui_check.py）

## 三、测试中发现并修复的缺陷（11 项）

| # | 严重度 | 缺陷 | 修复 |
|---|---|---|---|
| 1 | 高 | 力调电费公式符号与量纲错误：低于标准反被减免、比例 50 倍失真且恒触 ±15% 封顶 | 改为每档 0.01 加收 0.5% / 减免 0.15%，方向正确、封顶生效 |
| 2 | 高 | `login.html` 等根目录静态文件 404 —— 线上登录页无法访问 | 静态分发扩展 .html 等后缀白名单 + 文件存在性判断（防穿越） |
| 3 | 高 | `DELETE /api/webhooks/{id}` 与 `api_webhook_del(u,body,q,wid)` 形参不匹配 → 删除 500 | 路由参数统一为 `{wid}` |
| 4 | 高 | `DELETE /api/api-keys/{id}` 同样不匹配 → 删除 500 | 路由参数统一为 `{kid}` |
| 5 | 高 | 增量同步 `alarms` 实体引用不存在的 `at` 列 → 500 | 改用 `period` 列 |
| 6 | 中 | 需量预警阈值硬编码，业务规则改 `demand_warn_ratio` 不生效 | `api_demand_create` 从 `rules()` 动态读取阈值 |
| 7 | 中 | `/api/auth/me` 要求 `report.read`，抄表员等只读角色查不到自己信息 | 降为仅需登录 |
| 8 | 中 | 抄表员无 `read.check`，无法执行本职的抄表质检 | ROLE_PERMS 补齐 |
| 9 | 中 | 项目编号生成 `COUNT(*)+1` 与历史数据冲突风险 | 与告警编号一致，改为 MAX 尾号递增 + 空号探测 |
| 10 | 低 | `raise_alarm` 返回裸编号字符串，调用方无法拿到级别/类型 | 统一返回完整对象（no/level/atype/…） |
| 11 | 低 | 能效测试保存响应不含 value/grade，前端需二次解析 | 响应补 value/grade/metric/alarm |

## 六、遗留与建议

- 限流 300 次/分钟仅做放行验证，未做 429 触发（避免影响共享环境），上线后可通过压测确认
- Webhook 投递为异步线程 + 0/30/60/120s 退避，端到端重试已实现但未在测试中模拟接收端；建议对接方联调时用 `/apidoc` 所列 13 种事件做订阅验证
- 演示数据截至 2026-10，部署后系统按自然月滚动，无数据时看板为空属预期
